## 8. Remaining open questions

Structural / architectural questions that need answering before or during
early development, distinct from the parameter tuning in §9. Bigger-picture
"which shape is the pipeline?" items land here; "what value does knob X
take?" items land in §9.

1. **Read-level fallback arm** for samples too degraded to assemble ([brief.md §8.2](brief.md)). Defer to post-P5 unless P5 testing surfaces a clear need. More likely to bite at skim depth.
2. **Assembly strategy — bait-then-refine?** Do we try a quick-and-dirty draft assembly with read baiting, and then re-map clean reads back to that to pick up any reads that baiting didn't capture? Then assemble those reads properly? Structural question (adds a whole pass), not a knob — parking here rather than in §9.
3. **Organelle annotation strategy (stages 12–13a).** Partly resolved, partly open.

   **Resolved — the hand-rolled baseline.** A **single broad miniprot pass** against a comprehensive organellar protein panel ([§4.3](04-reference-data.md#43-protein-panel-and-barcode-selector)) supplies the protein-coding annotation for *every* assembly target, and the barcode FASTA is the subset of that annotation whose gene symbol appears in `assets/loci.json`. Rationale: one alignment cannot disagree with itself, so the locus drawn on the report's gene map is by construction the locus shipped to Taxodactyl ([rule 18](../CONSTITUTION.md)); and the pass costs nothing extra because miniprot was already required for extraction. This is specified in task 29_comprehensive_protein_panel.md and task 30_unified_locus_pass.md.

   **Open — is the hand-rolled baseline good enough, per arm?** miniprot is protein-to-genome only, so the baseline annotates **CDS features and nothing else**. Three gaps remain, and they matter differently per target:

   | Arm | Gap left by the broad miniprot pass | Off-the-shelf candidate |
   |---|---|---|
   | `animal_mt` | 22 of 37 canonical genes are tRNAs — the baseline shows barely a third of the mitogenome | **MITOS2** (bioconda, offline, covariance-model tRNA search). Adopted; see below. |
   | `plant_pt` | ~30 tRNAs, 4 rRNAs (8 loci with the IR), plus intron and *trans*-splicing structure (`rps12`) that miniprot calls as fragments | **Chloë** (best fit, but unlicensed and angiosperm-optimised — see task 32_research_plastid_noncds.md), **PGA** (GPL-3.0 but Perl and stale), or **tRNAscan-SE + barrnap** as a bioconda `mulled-build` bundle |
   | `plant_mt` | tRNAs and rRNAs; complicated by NUPT insertions carrying plastid-derived features that must not be annotated as mitochondrial | tRNAscan-SE + barrnap, subject to a NUPT cross-check |

   **The decision procedure is: benchmark the hand-rolled baseline against the off-the-shelf candidate for each arm independently, then pick per arm.** There is no requirement that all three arms use the same strategy — they have different gene complements, different tool availability, and different value. The benchmark method and acceptance criteria are §9 item 12.

   **MVP scoping.** `animal_mt` is the MVP arm and is decided: broad miniprot for CDS, MITOS2 for tRNA/rRNA, with MITOS2's own CDS calls retained as an independent cross-check rather than as features (task 31_annotate_merge.md). The plant arms need the research and benchmarking above before their strategy is fixed, so they ship on the hand-rolled baseline alone, emitting a CDS-only annotation explicitly labelled as such (`status: "ok_cds_only"`). This is a **provisional, honest** state, not a failure state — a plant sample receives a real annotation of every protein-coding gene found, with the missing feature classes stated rather than implied by absence ([principle 7](../CONSTITUTION.md)). See [§6](06-phases.md) P4a/P4b.

   Rejected outright: **GeSeq** — named in [brief.md §3.6](brief.md) but web-service only, with no CLI, so a containerised pipeline cannot use it ([rule 11](../CONSTITUTION.md)); the brief should be reconciled. **MitoFinder** — its only biocontainer is a 2022 Python 2.7 build ([rule 19](../CONSTITUTION.md)). See [this paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC9503105/pdf/ijms-23-10804.pdf) for a plant-annotator deep dive.
4. **Organelle map renderer (stage 14 `ORGANELLE_MAP`).** Tool choice deferred. **Input is GFF3 + `annotation_summary.json`, not GenBank** (see §7) — a candidate that only reads GenBank is disqualified unless it also reads GFF. Candidates: **[pyCirclize](https://github.com/moshi4/pyCirclize)** (Python, actively maintained; parses GFF as well as GenBank), **[plotgenes](https://github.com/aaronphillips7493/plotgenes)** (from CLAW's author), Circos with a custom GenBank→config converter, or an in-house Jinja+SVG renderer that reads GFF/GenBank directly (would fit the report renderer container per [§6a.5](06a-reports.md#6a5-report-implementation-boilerplate)). Inline SVG output preferred so it drops into the report. Decision needed before P4a.

## 9. Fine tuning (post-prototype benchmarking)

Items to benchmark **after** the first end-to-end prototype is running on
real data (roughly end of P3). Each entry is a knob or design choice where
we've picked a sensible default from prior art or first principles, but the
right value / choice will only become obvious with our own test data in
hand.

> **Do not benchmark against the integration fixtures.** They are
> correctness tests: subsampled to a 60-minute CI budget, drawn from old
> public SRA data that predates the R10.4.1 SUP chemistry this pipeline
> assumes, with one sample per target — and `plant_pt` / `plant_mt` are
> the *same* accession. Tuning a threshold until the fixtures pass is
> circular, because the fixture bounds were set from the same
> under-powered data; task 28 §10.2 is a worked example of that going
> wrong. Every experiment below needs the P3 datasets, and real
> performance should be materially better than any fixture-derived
> figure. See [§5.1](05-test-data.md#51-the-integration-fixtures-are-correctness-tests-not-benchmarks).

**Flye tuning reference.** For items 3–6 and 9 below (all Flye knobs), the
authoritative source for parameter behaviour, valid combinations, and
mode-specific caveats is the vendored
[Flye user guide](../reference-material/flye-user-guide.md). Consult it
before designing any Flye benchmark — it documents the `--meta` /
`--asm-coverage` incompatibility, read-mode implications for polishing
iterations, and `--genome-size` estimator behaviour that these experiments
depend on.
